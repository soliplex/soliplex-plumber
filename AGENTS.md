# AGENTS.md

Guidance for AI coding agents working on `soliplex-plumber`. (`CLAUDE.md` is
a thin stub that imports this file so Claude Code loads it automatically.)

## Project Overview

`soliplex-plumber` reads and modifies the configuration of an *existing*
Soliplex stack -- one generated by
[`soliplex-template`](https://github.com/soliplex/soliplex-template). It is
a library plus one console script (`soliplex-config`), not a Soliplex
application, and it does not depend on the `soliplex` package.

It is the shared dependency of the skill projects that operate on a
generated stack -- the `soliplex-template` skill's `add_room.py` and the
`soliplex-concierge` installer -- so the stack-wiring rules live in one
place. Treat the public API of its modules accordingly: see
[Public API changes](#public-api-changes).

## Build and Test

```bash
# Install dependencies (use uv, not pip)
uv sync --group dev

# Run unit tests with the 100% coverage requirement
uv run pytest

# Run a specific test file / test.  '--no-cov' is required: 'addopts'
# always applies the 100% gate, which a partial run cannot satisfy.
uv run pytest --no-cov tests/unit/test_rooms.py
uv run pytest --no-cov tests/unit/test_rooms.py::test_name

# Lint and format
uv run ruff check
uv run ruff format --check

# Auto-fix lint and format issues
uv run ruff check --fix
uv run ruff format

# Build the documentation site (docs/ -> site/); needs the 'docs' group
uv sync --group docs
uv run zensical build
```

## Code Style

- Line length: 79 characters
- Single-line imports enforced (isort via ruff)
- Ruff rule sets: F, E, B, U, I, PD, TRY, PT
- Supported Python: 3.13 and later (`requires-python = ">=3.13"`)
- Use `uv run` to execute all Python commands
- Open text files with an explicit `encoding=` (enforced in
  `src/soliplex_plumber/` by the `lint-textio` hook below)

## Pre-commit Hooks

Optional: `uv run pre-commit install` automates the CI checks before each
commit (`uv run pre-commit run --all-files` runs them once against the whole
tree). The configured hooks (see `.pre-commit-config.yaml`) enforce:

- `ruff-check` / `ruff-format` -- lint and format Python sources
- `pymarkdown` -- lint Markdown files
- `lint-textio` -- reject text file IO in `src/soliplex_plumber/` without
  an explicit `encoding=` (falls back to the host locale encoding, `cp1252`
  on Windows); `scripts/lint_textio.py`, stdlib-only
- `lint-textio-self-test` -- run `scripts/lint_textio.py --self-test` when
  that script itself changes, so a check gone blind fails loudly instead of
  passing by finding nothing
- `actionlint` -- lint GitHub Actions workflow files
- `check-toml` / `check-yaml` -- validate TOML and YAML syntax
- `gitleaks` -- scan for committed secrets
- `pip-audit` -- scan dependencies for known vulnerabilities (runs when
  `pyproject.toml`, `uv.lock`, or `.pre-commit-config.yaml` changes)
- `debug-statements` -- reject leftover `pdb` / `breakpoint()` calls
- `trailing-whitespace` / `end-of-file-fixer` -- normalize whitespace
- `check-merge-conflict` -- reject unresolved merge-conflict markers
- `no-commit-to-branch` -- block direct commits to `main` / `master`, so
  create a branch before committing

## Testing Requirements

- Unit tests live in `tests/unit/`, one `test_<module>.py` per module in
  `src/soliplex_plumber/`; shared fixtures are in `tests/unit/conftest.py`
- 100% branch coverage is enforced via pytest-cov (`--cov-fail-under=100`)
  of both the package and the test suite (see `addopts` in
  `pyproject.toml`)
- `--cov-fail-under=100` lives in `addopts`, so it applies to *every*
  `pytest` invocation, not just full runs. Pass `--no-cov` when running a
  subset -- a single file or a single test -- otherwise the run fails on
  the threshold no matter how the tests themselves fared
- The unit tests need neither Docker nor a running stack. `stack` and
  `soliplex_config` are tested by mocking their `shutil.which` and
  `subprocess.run` seams; the rest work on stacks built under `tmp_path`.
  Keep it that way: never add a test that shells out to `docker`
- **The suite runs on Windows too.** `.github/workflows/python-test.yaml`
  runs it on Linux (Python 3.13 and 3.14) and on `windows-latest` (3.13
  only), and the 100% gate applies to every job. An assertion on a rendered
  path should build its expectation with `pathlib` so it holds on either
  separator; never loosen an assertion to make a platform pass

## Repository Structure

- `src/soliplex_plumber/` -- the package (`hatchling`, built from
  `src/soliplex_plumber`)
  - `sections.py` -- declarative catalog of `installation.yaml` sections
    and the default the backend applies when each is absent. It mirrors
    `soliplex.config.installation` (the source of truth): keep it in sync
  - `installation.py` -- pure, comment-preserving `text -> (new_text,
    action)` editors that splice list items into one section, line-based
  - `rooms.py` -- install a room into a stack (`resolve_project`,
    `install_room`, `install_room_from`) and wire its `room_paths` entry;
    edits are append-only, so installing a room never disables another
  - `stack.py` -- run a stack's `soliplex-cli` in a throwaway
    `docker compose run --rm` container; needs Docker
  - `soliplex_config.py` -- query a *running* stack's resolved config
    (`show` / `get` / `rooms` / `room`); the `soliplex-config` script.
    Builds on `stack`
- `tests/unit/` -- the unit suite (100% coverage required)
- `scripts/lint_textio.py` -- the `lint-textio` pre-commit check
- `docs/` -- the published documentation (Zensical, configured by
  `zensical.toml`): `usage/` how-to pages and `reference/api.md`

The core (`sections`, `installation`, `rooms`) does pure filesystem work:
no Docker, no running backend. Keep Docker-dependent code in `stack` and
the modules built on it.

## Public API changes

Downstream projects (`soliplex-template`'s `add_room.py`, the
`soliplex-concierge` installer) pin to released versions of this package,
so a breaking change to a public function or its signature goes through a
deprecation cycle rather than landing at once:

- keep the old form working for one minor release, emitting a
  `DeprecationWarning` that names the replacement
- remove it in a later minor release, and note the removal in the release
  notes

For example, `rooms.install_room{,_from}` became keyword-only in v0.4
(PR #14) with the positional forms deprecated, and the positional forms
were removed in v0.5 (PR #21).

## Entry Points

- `soliplex-config` -- query a running stack's resolved installation
  config; `soliplex_plumber.soliplex_config:run`. Run
  `uv run soliplex-config --help` for usage

## Documentation

Configuration and usage docs are in [docs/](docs/) (built with Zensical,
published to <https://soliplex.github.io/soliplex-plumber/> by
`.github/workflows/docs.yaml`). A change to a module's public behavior
should update its page under `docs/usage/` (`soliplex_config` is documented
in `soliplex-config.md`). The API reference, `docs/reference/api.md`, is
written by hand, so a change that adds, removes, or renames a public name
must update it too.
